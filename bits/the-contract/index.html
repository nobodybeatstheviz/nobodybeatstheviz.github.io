#What it is

dbt runs SQL inside the warehouse, here BigQuery, and turns raw tables into tested, documented, reusable ones. The 178 games join to Retrosheet, the official play-by-play, on one clean key. From there: 16 models, seven staging views that rename and cast and filter, eight marts that join and add meaning, one calendar table the metric engine needs. One fact table with 178 rows, one per game, carrying pre-computed answers like whether it was a Yankees game and who won.

On top of the marts sits the semantic layer, shipped 2026-08-31: five semantic models and nine metrics. Seven of the nine are the governed questions. Games attended. Unique stadiums. Home runs witnessed. Runs witnessed. Win rate when I'm there. Games per companion. Hall of Famers seen. Each is a few lines of YAML naming a measure and how to aggregate it. home_runs_witnessed is a count of plays where the event code is 23, filtered to games I attended. That's the whole definition, and it appears in exactly one file.

This is the reference. Every other engine in the run, Snowflake and Databricks and Data 360 and Tableau Next, is measured against what this layer says. The reference answers were recorded 2026-08-31: 178 games in 22 stadiums, 400 home runs, 1,706 runs, 44 Hall of Famers, Yankees 90–53 in the 143 decided games I sat through.

#The test that failed on purpose

A uniqueness test on Retrosheet's game id failed with 1,872 duplicates. That looked like a disaster for about ten minutes. Then it looked like the useful result: the public dataset includes Negro Leagues, exhibitions, and pre-MLB games for completeness, and some of them share ids with the modern schedule. My staging filter already kept only my 178, so nothing downstream was ever wrong.

The choice was about test granularity. Drop the test on the source I don't control, document the finding in the source's description, and keep the test where it applies, on the tables I do control. A test that fails and teaches you something about your source is doing its job. A test that fails on somebody else's data forever is noise.

Two smaller ones: an all-empty text column made dbt infer it as a number and broke a trim, fixed by pinning the type in the seed config. And the newest dbt engine turned out to have no local metric engine at all, so the metrics are queried through a side-by-side older install. Free, local, and in the same terminal as everything else.

#What it taught me

  1. The calculated field didn't go away. It got a home. Everything you know about what a home run is, what a decided game is, who counts as a companion, is exactly the knowledge the semantic layer is for. It moves upstream of the workbook and every tool reads it. Your fifteen years of knowing what the field means is the asset here, not the deprecated part.
  2. Filter early. Keeping only my 178 games in staging cuts each run to about 34 MB of scan instead of all of baseball history. The same push-down instinct you have with an extract filter, one layer earlier.
  3. The reference has to exist before parity means anything. Six engines agreeing is only interesting if one of them is the contract. This is the one.
