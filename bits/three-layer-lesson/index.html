THE THREE-LAYER LESSON

The VLOOKUPs were in the printed tab.

Source, analysis, presentation. Three layers that never touch — the first page of every data-modeling book, and a line I held for clients for two decades. Then I built my own operating system with an agent, and broke it in exactly the way I'd flag in anyone else's work. This is the arithmetic, and the fix.

Claude Code git Markdown Python generators Architecture

#What it is

Every bad spreadsheet I have ever been handed breaks the same rule: somebody put the VLOOKUPs in the tab they print. Analysis and presentation fused into one artifact. One input changes and there is no way to regenerate — only to repair, by hand, forever. That was never a spreadsheet problem. It's an architecture problem that shows up in spreadsheets first.

Over four months I built a personal operating system in markdown, run through Claude Code — job search, builds, practices, the whole life. The Source layer was right: one canonical file per fact. The Analysis layer was mostly missing. And the Presentation layer was twenty-five hand-maintained index files, a weekly dashboard, a cross-project tracker — each one restating facts that lived somewhere else.

The number that made it undeniable: one logical change cost eight file edits. Closing eleven job applications in a single day meant touching the eleven source files plus six derived ones. Two of the six were generated and corrected themselves. The other four were stale before the session ended. Not a discipline failure. Write amplification, and it's structural.

#How it works

Why would somebody with receipts going back to ’09 suspend a model he'd trusted the whole time? Because I read the problem as new. “Context engineering,” “memory,” “AI system” — the vocabulary made it feel like a domain with its own physics, where the answer was put everything somewhere the model can see it. So every cleanup pass tightened the copies: more indexes, more cross-references, more summaries. The exact opposite of the fix. I was maintaining the caches instead of eliminating them.

The correction is the same three layers, with the new tools in their right seats:

  • Source — read, never own. git history plus each fact's one canonical home. A probabilistic writer against a system of record produces corruption you can't audit or unwind.
  • Analysis — the sweet spot, and genuinely new. Judgment over unstructured input: reading two hundred job descriptions and deciding which bar is real. No prior tool did the interpretive half of analysis. Excel did arithmetic. SQL did set logic. This does judgment under ambiguity.
  • Presentation — generate the view, never maintain it. Indexes, dashboards, registers: if a file has an upstream source, a script derives it. If it can't be generated, it shouldn't exist.

Which collapses to one line: the agent's job is to write the generator, not to be the generator. Agents are a compiler, not a runtime. Every time I asked the agent to be the runtime — to re-derive state each session from prose instructions — I paid for a non-deterministic answer to a question that had a deterministic one.

The situational rule that falls out, and it explains which of my projects landed and which sprawled: does this repeat, and does it accumulate state? No — let the agent do all three layers; a one-off analysis, a draft, a decision. Yes — the agent's only job is to build the mechanism. Then the mechanism runs, not the agent.

#What it taught me

  1. The database era held the boundary for me, and I stopped noticing. You physically could not write to the warehouse from a dashboard. A whole career in a world where the tooling enforced the separation, then a tool with file-write access to all three layers in any order — and I kept the assumption that separation was handled. Agentic tooling returns you to Excel's fused-layer world at machine speed. Excel let you make this mistake one workbook at a time. An agent makes it across twenty-five files in a session, cheerfully, while you're grateful for the help.
  2. One home is not the same as correct. Single-home eliminates drift. It does not make the fact true. The first production run of the fixed machinery pulled a wrong transcription from the right place and propagated it straight into a build. What caught it was re-reading the external source at the moment it became load-bearing. The tooling can enforce separation; it cannot enforce accuracy. That still costs a measurement.
  3. Convert prescription into mechanism. Where a rule kept getting skipped, prose never fixed it. Writing “do the dedup properly” into a procedure failed on the very next run. Making the dedup a script that either ran or didn't could not fail the same way. That's the line I'd give a client.
  4. Git is the Source layer for history. Not a backup: an append-only log of every state the work has been in, with a human note on each entry saying why. So no document carries its own changelog. The doc holds what's true today; the commit message holds how it got that way.

Why it's the story and not just a cleanup: the thesis, demonstrated on myself. Same questions. New tools. The question — how do you separate source from derivation from presentation — did not change because the tool became a model and the storage became markdown. Every organization adopting AI right now is making this mistake at scale: dumping context into retrieval layers, hand-maintaining summaries, calling the drift a prompt problem. The correction isn't a better prompt. It's the layering they already know and stopped applying the moment the tool changed.

The operating system is a private repo. The README tells the git half of the story.
